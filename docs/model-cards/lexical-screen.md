# Lexical task screen v0.1.0
## Identity and purpose
Method: lexical-screen-v0.1.0. Rubric: task-review-v0.1.0. Scenario date: 2026-10-29. Status: experimental, unvalidated review aid. This is a deterministic rule baseline; no learned weights, LLM API or training process is used.

## Inputs and outputs
Input: original O*NET task statement plus a trusted, versioned project config. Occupation title, personal characteristics, salary and geography are not screening inputs. Output: exact matched text spans, dimension cues/unknowns, guard hits and a review-routing category. Scalar exposure, human dependency and final workflow label remain null.

## Intended use
Help researchers inspect and refine an independent annotation protocol. Development suggestions are separate from blind reviewer queues. Holdout suggestions are not generated by the pilot preparation script. The baseline does not determine whether a person should be hired, dismissed or paid differently.

## Data and sampling
The pinned O*NET 31.0 source is described in [source cards](../data-cards/core-sources.md). The [pilot report](../reports/task-pilot.json) records a purposive 20-occupation/200-task sample, with the eight known case studies confined to development. Occupation groups linked by detected selected-text duplicates stay in one split. Sampling is not representative; semantic leakage review is pending.

## Evaluation status
Unit tests check evidence spans, negation/safety guards, unknown handling, deterministic sampling and review-integrity gates. The real-data run checks artifact reproducibility and split boundaries. These are engineering checks, not model accuracy. No completed independent human reviews, agreement metrics, macro-F1, calibration, time-saving measurement or replacement prediction exists.

The current development run routes 112 of 160 tasks to insufficient_evidence. That count measures lexical noncoverage only. Neither the remaining routes nor noncoverage are a workforce exposure estimate. See the report for exact route counts and version hashes.

## Limitations and risks
Regex rules cannot establish actual feasibility, implicit context, cultural knowledge, judgment, quality or causal employment impact. Exact lexical cues may produce false positives; missing synonyms and task decompositions produce false negatives. Negation scope is conservative and incomplete. The safety guard is not a comprehensive safety classifier. Model confidence is not emitted.

## Reproduction and changes
Run scripts/prepare_task_pilot.py after the core build, then scripts/validate_task_reviews.py on the run directory. Run identity hashes code, rubric, cohort and source fingerprint; files have content checksums. Changes create a new run, and modified existing review artifacts are never overwritten. Human-reviewed improvements require a new confirmatory evaluation design before performance claims.
